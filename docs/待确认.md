
# Super 语言设计规范与决策清单 (v0.0.1 )

> **项目背景**：Super 是一门支持自动推导所有权、显式错误处理 (`return err`)，并提供内置构建工具链的现代系统级编程语言。
> **实现路线图**：C 语言引导（Bootstrap） -> 自举（Self-Hosting） -> Go 语言重写（Rewrite）。

## 一、 词法与语法层面 (Lexical & Syntax)

**1.1 数组解析歧义（已确认设计）**
*   **现状**：`arr = {"1", "2", "3"}[3]` 采用“先写字面量，后置长度”的设计，以解决动态添加元素时还需回头修改长度的痛点。
*   **待决**：编译器如何区分 `arr[3]` 是“声明长度为3的数组”还是“取数组的第4个元素”？
*   **建议规则**：规定 `数组字面量` 后缀 `[n]` 只能用于变量声明初始化阶段；对于已声明变量的 `arr[n]` 一律作为索引访问。

**1.2 运算符歧义（已修改）**
*   **现状**：原笔记中 `^=` 被定义为乘方，`^` 被定义为异或。
*   **决策**：乘方符号需要修改，避免与 C 家族习惯的按位异或赋值产生混淆。
*   **待决**：乘方操作符是改为 `**` 还是提供内置函数 `pow()`？异或 `^` 保持不变。

**1.3 循环语法的分隔符（已修改）**
*   **现状**：原笔记 `for i int=0, i<=10, i++` 使用了逗号分隔。
*   **决策**：改为分号 `;` 分隔。
*   **新语法**：`for i int=0; i<=10; i++ { }`

**1.4 方法的接收者语法**
*   **现状**：`fn (a int a) example -> int`，变量名与类型名重复。
*   **待决**：标准写法是 `fn (a int) example` 还是 `fn (a: int) example`？

**1.5 指针符号的冲突**
*   **现状**：`*a = &b` 使用了 `*` 作为解引用，`&` 作为取地址。
*   **待决**：变量声明中如何表示指针类型？`*` 同时用于乘法，语法解析器（Parser）需明确区分上下文。

**1.6 输入语句语义（已修改）**
*   **现状**：`a = in` 和 `a = in("input: ")` 并存。
*   **决策**：`in` 等于 C++ 的 `cin`，Python 的 `input`。即标准输入读取。
*   **新语义**：`a = in` 等同于读取一行标准输入，`a = in("input: ")` 等同于输出提示后读取一行输入。

## 二、 类型系统与内存管理 (Type System & Memory)

**2.1 所有权自动推导的边界**
*   **现状**：语言在编译期自动推导所有权，无需开发者手写生命周期注解。
*   **待决**：面对 `*a = &b; *a = 10` 这种裸指针操作，编译器是直接拒绝（强制要求写 `unsafe` 块），还是允许它破坏自动所有权系统？

**2.2 `#GC` 宏的生效机制**
*   **现状**：支持 `#GC = True` 和 `#GC = False` 编译指令。
*   **待决**：这是全局编译选项、文件级别还是块级别？`#GC = False` 时是否需要开发者手动 `free`？如果不 `free`，编译器会在编译期报错吗？

**2.3 动态数组 vs 固定数组**
*   **现状**：`{...}[3]` 代表固定长度数组（栈分配）。
*   **待决**：语言是否支持动态数组（堆分配、动态扩容）？如果只有定长数组，后续如何添加元素？

**2.4 类型转换与推导**
*   **现状**：`type a int.` 定义了新类型。
*   **待决**：`a` 与 `int` 之间是隐式转换还是必须显式 `a(10)`？`longint` 和 `int` 混用时的类型提升规则是什么？

**2.5 结构体的内存对齐**
*   **待决**：`struct a { a int }` 的内存布局是否遵循 C 的默认对齐规则？是否提供类似 `#pack` 的宏来指定紧凑内存布局？

## 三、 控制流与错误处理 (Control Flow & Error)

**3.1 `return err` 的规范形态**
*   **现状**：错误处理采用显式 `return err`。
*   **待决**：具体是返回一个字符串，还是返回一个结构体？调用 `fn a() -> int` 时，如果出错了，返回的 `err` 如何强制处理？

**3.2 错误传播的语法糖（已修改）**
*   **决策**：与 Go 语言一样（Go 风格）。
*   **实现**：不使用问号 `?` 语法糖，而是强制开发者显式写出：
    ```super
    v, err := a()
    if err != nil {
        return err
    }
    ```

**3.3 `switch` 的匹配规则**
*   **现状**：`switch 4 { "1": ... }`，`4` 是整型，`"1"` 是字符串。
*   **待决**：这是否意味着 Switch 支持弱类型匹配？是否必须有默认的 `default` 分支？

**3.4 `say` 和 `listen` 的并发模型**
*   **现状**：内置广播通信机制。
*   **待决**：它们是同步阻塞的还是异步非阻塞的？底层打算用 C 的 pthread、epoll 还是其他机制实现？

## 四、 面向对象与模块化 (OOP & Modularity)

**4.1 接口的实现机制**
*   **现状**：`interface example { a() b() }`
*   **待决**：是鸭子类型（隐含实现）还是需要显式 `impl` 声明？两个接口有同名方法时如何解决二义性？

**4.2 包与导入的循环依赖**
*   **待决**：`main.super` 导入 `fmt`，`fmt` 导入 `os`，`os` 又导入 `main` 时，是直接报错还是允许前置声明？

**4.3 `include` 和 `#main` 的关系**
*   **待决**：`include fmt` 是导入整个包还是某个文件？`#main` 是文件入口点还是包声明？

**4.4 `pub fn` 的可见性**
*   **待决**：只有全局函数才能 `pub` 吗？`struct` 和 `interface` 的字段是否有私有/公有之分？

## 五、 工具链与构建系统 (Toolchain & Build)

**5.1 `super file --makefile` 的破坏性**
*   **现状**：把 `#code-code#` 部分形成 Makefile 且 `File.super` 删除。
*   **待决**：如果后续需要修改构建指令，没有源文件怎么办？建议保留 `#code` 在 `.super` 中，仅更新生成的 `Makefile`。

**5.2 `Settings.toml` 与 `File.super` 的关系**
*   **待决**：两者配置职责如何划分？是否会造成配置冗余？

**5.3 依赖版本控制**
*   **待决**：`super mod tidy` 整理依赖时，版本号写在哪里？依赖源是本地路径还是远程仓库？

**5.4 `super error` 的错误码规范**
*   **待决**：错误码是否分段设计（如 1000-1999 为词法错误）？错误信息是否支持多语言？

## 六、 实现路线图落地 (Implementation Strategy)

**6.1 C 语言引导阶段的 AST 设计**
*   **待决**：用什么数据结构表示 AST？联合体（union）+ 结构体，还是虚函数表？

**6.2 C 阶段的内存管理**
*   **待决**：写 C 编译器时，会先写 Arena Allocator（内存池）还是直接 `malloc/free` 以避免内存泄漏？

**6.3 自举阶段的核心库最小集**
*   **待决**：用 Super 写编译器，最基础的必备库（字符串、哈希表、动态数组、文件 I/O）完备了吗？

**6.4 Go 重写阶段的兼容性**
*   **待决**：如何保证 Go 版本与 C 版本行为一致？需要构建包含数千用例的“黄金测试集”进行双边对比吗？

**6.5 目标代码生成**
*   **待决**：在 C 阶段，是直接生成汇编、生成 C 代码（Transpiler），还是生成 LLVM IR？
